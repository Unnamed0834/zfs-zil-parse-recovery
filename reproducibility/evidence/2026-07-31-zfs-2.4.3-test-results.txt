ZFS 2.4.3 test run: closing the version-coverage gap
=====================================================

Date:  2026-07-31
Host:  Apple Silicon (arm64), macOS 26.6, Lima 2.2.0 (vz)
Guest: Debian 13 (Trixie), kernel 6.12.95+deb13-cloud-arm64, aarch64
VM:    zfs243
ZFS:   built from source, tag zfs-2.4.3


WHY THIS RUN EXISTS
-------------------
Every previous result in this repository was produced on ZFS 2.2.2, the
zfs-2.3.4 release tag, or 2.4.1. On 2026-07-31 it was found that **none of
those three trees contains amotin's 1e1d64d** ("Fix log vdev removal issues",
2026-03-04, closes openzfs/zfs#18277). That commit first ships in zfs-2.4.3.

Two consequences, both recorded as ../../CLAIMS.md 3.29:

  (a) The "2.4.x is already hardened by 1e1d64d" hypothesis behind FINDINGS.md
      finding 13 was never actually tested. All three trees compared lack the
      hardening, so their agreeing with one another proved nothing about it.

  (b) zfs-2.4.3 is also the tree the incident repair was built on
      (module string: zfs-2.4.3-0-g83020cf-dirty-dist). So the fix ran with
      1e1d64d plus Patches A-D on top, while the testing ran without 1e1d64d
      at all.

This run closes (a) and (b).

IT DOES NOT TEST WHETHER 1e1d64d WOULD HAVE PREVENTED THE INCIDENT. It would
not. 1e1d64d tests BP_IS_HOLE(&zh->zh_log) -- an ALL-ZERO DVA. The incident
pool held a VALID, NON-ZERO DVA whose vdev index resolved to a hole, which
that test does not match (CLAIMS.md 3.5, 3.2). The affected machine was a
fresh, fully-updated install of the then-current TrueNAS release and hung
anyway. The gap in zil_check_log_chain() is independent of this.

spa_namespace_lock is still held, so every subsequent zpool command blocks.
Recovery required `limactl stop --force zfs243`.


ONE GENUINE DIFFERENCE FROM 2.2.2: txg_quiesce IS NOT WEDGED
-------------------------------------------------------------
On 2.2.2 the capture showed two D-state tasks:

  10466 D    txg_quiesce
  10725 D    zpool

On 2.4.3 there is only one:

  60246 D    zpool

and `dmesg | grep -c txg_quiesce` returns 0 -- the txg_quiesce thread never
blocked and never tripped the hung-task watchdog.

This is the first behavioural difference between versions found anywhere in
this reproduction work, and it should be reported accurately:

  - CLAIMS.md 2.2 ("the hang also wedges txg_quiesce, stalling the entire
    pool") is REPRODUCED on 2.2.2 and NOT REPRODUCED on 2.4.3.
  - CLAIMS.md 2.1 (the hang itself) and 2.3 (unkillable, holds
    spa_namespace_lock, needs a power cycle) are reproduced on BOTH.

The practical outcome is unchanged -- the machine still needs a forced power
cycle, and every zpool command still blocks -- but the blast radius is
narrower on 2.4.3 than the 2.2.2 capture suggests. A bug report should not
claim the whole pool stalls on current releases without saying which version
that was seen on.

Whether this is a deliberate improvement or an artifact of timing (the run was
observed for ~165 s; txg_quiesce might block later under sustained write load)
was NOT determined. Treat it as observed-not-explained.


WHAT THIS RUN ESTABLISHES
-------------------------
- The precondition remains unreachable by routes C, D and G on zfs-2.4.3,
  the only release containing 1e1d64d. Claim 3.20's bounded negative now
  spans four releases instead of three, including the hardened one.
- CLAIMS.md 4.5 can move from UNTESTED to DISPROVED: 2.4.3 is NOT hardened
  against these paths relative to 2.3.4. It behaves identically.
- The finding-10 hang survives into 2.4.3, WITH a captured stack. The newest
  release is no longer the untested one for this defect. Reporting the hang
  no longer needs the caveat "newest version tested is 2.3.4".
- The two sides of this repository now share a tree: the reproduction has
  been run on the same commit (83020cf) the incident repair was built from.

WHAT IT DOES NOT ESTABLISH
--------------------------
- Anything about failmode. This run used the default failmode=wait, like
  every other run in ATTEMPTS.md. FAILMODE=continue is still untested on
  every version. See CLAIMS.md 2.6 and 4.9.
- Anything about routes A/F (script 05), the freeze route, or the offline
  route on 2.4.3. Only 01, 03, 04, 06 and 07 were run here.
- Anything about TrueNAS's own build, middleware, or x86-64.
- Whether the corrected form of Patch A works. Nothing was patched in this
  VM; it is a clean release-tag build. See CLAIMS.md 1.12.
