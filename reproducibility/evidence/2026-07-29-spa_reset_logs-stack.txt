NOTE ON SUPERSESSION
--------------------
The IMPLICATION section below is the original framing from the day this stack
was captured. It is preserved verbatim. The conclusion it states ("log removal
is not atomic with respect to ZIL cleanup") was later corrected by FINDINGS.md
finding 9: the removal IS atomic in terms of returning errors; the actual gap
is that `spa_reset_logs()` is skipped entirely when `vs_alloc == 0`, returning
no error at all. That skipping of the reset (not an atomicity bug) is the
mechanism that allows the affected pool's state to arise. See
`../FINDINGS.md` finding 9 and `../../CLAIMS.md` 4.1 (INFERRED).

WHAT THIS SHOWS
---------------
`zpool remove <pool> <logdev>` issued against a FROZEN pool blocks in
uninterruptible sleep. The stack proves that log-vdev removal walks every
dataset and resets its ZIL before the vdev is converted to a hole:

    spa_vdev_remove -> spa_reset_logs -> dmu_objset_find
      -> zil_reset -> zil_suspend -> zil_commit_impl

On a frozen pool no transaction group can sync, so zil_commit_impl never
completes and the removal never returns.

IMPLICATION
-----------
A dangling ZIL header pointing at a hole vdev can only exist if
spa_reset_logs() failed for at least one dataset while spa_vdev_remove()
proceeded anyway. Log removal is not atomic with respect to ZIL cleanup.

HOW REPRODUCED
--------------
    zpool create -o cachefile=none -O sync=always t2 <disk> log <slog>
    zpool freeze t2
    for i in 1 2 3 4 5; do
        dd if=/dev/urandom of=/t2/f$i bs=128k count=4 oflag=sync
    done
    zpool remove t2 <slog>        # blocks
    # in another shell:
    ps -eo pid,stat,comm | awk '$2 ~ /D/'
    cat /proc/<pid>/stack
