WHAT THIS SHOWS
---------------
`zpool remove <pool> <logdev>` hangs UNKILLABLY when the log device's backing
store is returning I/O errors. spa_reset_logs() walks datasets, and for a
dataset with a live ZIL chain it reaches zil_parse(), which issues reads
against the dead device and blocks in zio_wait().

CORRECTION (added after capture)
--------------------------------
The line above originally read "...blocks in zio_wait() with no error path".
That was wrong. zil_parse() DOES have an error path: it returns int, checks the
return of zil_read_log_block(), warns via cmn_err, and breaks the loop. The
error path is simply never reached here, because the ZIO does not complete and
zio_wait() never returns.

Why the ZIO does not complete was NOT established. This capture was taken with
the pool at the default failmode=wait; no run with continue or panic has been
performed. (Note that on the incident hardware failmode could not be reached
during the load at all, for reasons confirmed in source -- see ../../CLAIMS.md
3.23 and 3.24. The test environment does not have that constraint, because it creates its
own pools: FAILMODE=continue sudo -E ./07-path-h-yank-live-log.sh.)

Do not assume failmode is the answer. ../../CLAIMS.md 4.9 argues from source
that a read whose DVA resolves to a hole should fail fast with ENOTSUP and
never block, whatever failmode is set to. It blocked anyway. That is the
sharpest open question here.

See ../../CLAIMS.md 2.5, 2.6 and 4.9.

This is the same defect class as the import-time hang that made the affected
incident pool unimportable, but in the REMOVAL path rather than the import path:

  import-time:  zil_check_log_chain -> zil_parse -> arc_read -> zio_wait
  removal-time: zil_destroy_sync    -> zil_parse -> arc_read -> zio_wait

REPRODUCED ON STOCK ZFS 2.2.2. No patched module, no exotic hardware.

HOW REPRODUCED
--------------
See 07-path-h-yank-live-log.sh. Summary:

  1. back the log with file -> loop -> dm-linear so it can be failed on demand
       losetup --find --show /var/tmp/ziltest/slog
       dmsetup create slogdev --table "0 <sectors> linear /dev/loopN 0"
  2. zpool create -O sync=always ziltest <d1> <d2> log /dev/mapper/slogdev
     zfs create ziltest/ds1
  3. drive synchronous writes so the ZIL chain is live on the log device
  4. zfs unmount ziltest/ds1     (so its ZIL cannot drain and zh_log stays set)
  5. fail the device WITHOUT exporting the pool:
       dmsetup suspend slogdev
       dmsetup load    slogdev --table "0 <sectors> error"
       dmsetup resume  slogdev
  6. zpool remove ziltest <logdev>      <-- hangs forever here

The pool must stay imported throughout. Exporting and re-importing with -m
clears every zh_log via the SPA_LOG_CLEAR path in zil_claim(), which removes
the condition.

WHY THIS MATTERS FOR THE AFFECTED POOL
--------------------------------------
The affected pool's SLOG was a pair of SSDs flickering between available and
unavailable. Any `zpool remove` attempted in that state would hang exactly
like this. The pool's own history records
`2026-07-19.22:57:28  py-libzfs: zpool remove storageNone`, which is
consistent with a removal attempt that did not complete cleanly.

RELATIONSHIP TO THE vs_alloc GATE
---------------------------------
vdev_removal.c, spa_vdev_remove_log():

    if (vd->vdev_stat.vs_alloc != 0)
            error = spa_reset_logs(spa);

Two failure modes follow, and neither ends cleanly:

  vs_alloc != 0 and the device is failing
      -> spa_reset_logs() runs, reaches zil_parse(), hangs forever (this file)

  vs_alloc == 0 (device wiped or absent)
      -> spa_reset_logs() is SKIPPED, the removal succeeds, and any dataset
         holding a non-zero zh_log keeps a dangling reference into the hole
         that the removal creates (confirmed in 06-path-g-vs-alloc-zero.sh:
         log showed ALLOC 0, remove exit=0, hole created)
