WHAT THIS TESTS
---------------
Finding 16 showed that a hole vdev plus a dangling non-zero zh_log DVA
resolving to it does NOT hang a writable import on zfs-2.4.3. The stated
reason was that an UNCLAIMED chain is read with ZIO_FLAG_SPECULATIVE
(zil.c:256-257) and the resulting ECKSUM/ENOENT is swallowed at zil.c:1328.

The obvious follow-up was a CLAIMED chain: once zh_claim_txg != 0 the
SPECULATIVE flag is not set, so the failure should propagate rather than be
absorbed. That variant was recorded as untested and as the leading candidate
for whatever the incident had that the synthesis did not.

It is now tested. It does not hang either.

RESULT 2: the failure is spa_load_verify, via the hole-vdev blkptr check
-------------------------------------------------------------------------
The import dies at "Verifying pool data" -- spa_load_verify() -- with
error=5 (EIO), because a metadata blkptr fails validation:

    zio.c:1135: ziltest: blkptr at ... DVA 0 has hole VDEV 2

Source path, checked against the zfs-2.4.3 tag:

  - traverse_zil_block(), module/zfs/dmu_traverse.c:93-98:

        if (BP_IS_HOLE(bp))
                return (0);
        if (claim_txg == 0 &&
            get_birth_time(td, bp) >= spa_min_claim_txg(td->td_spa))
                return (-1);

    An UNCLAIMED chain (claim_txg == 0) with a recent birth txg is skipped
    here and never handed to the traversal callback. That is why finding 16's
    unclaimed variant imported cleanly: spa_load_verify never looked at the
    bad blkptr at all.

    Once claim_txg != 0 the guard does not fire, the block IS traversed, and

  - zfs_blkptr_verify(), module/zfs/zio.c:1271 (the format string
    "blkptr at %px DVA %u has hole VDEV %llu"; emitted at runtime through
    zfs_blkptr_verify_log() at zio.c:1135)

    rejects it because the DVA's vdev index resolves to a hole. spa_load_verify
    counts it as a metadata error and the load fails with EIO.


RESULT 3: the "unexplained label artifact" from finding 16 is now explained
----------------------------------------------------------------------------
2026-07-31-precondition-synthesis.txt records, under "AN UNEXPLAINED ARTIFACT":

    vdev.c:185: ... best uberblock found for spa ziltest, txg=42
    vdev.c:185: ... label discarded as txg is too large (51 > 42)
    vdev.c:185: ... failed to read label config
    spa_misc.c:417: spa_load_failed(...): FAILED: label config unavailable

  and says "Cause NOT determined. The likely reading is that skipping
  spa_reset_logs() leaves the pool subtly inconsistent ... i.e. an artifact of
  the debug hook, not of the hole."

**That reading was wrong.** The full dbgmsg above shows the label messages are
not the primary failure and have nothing to do with the debug hook. The
sequence is:

    1. spa_load_verify fails with EIO on the hole-vdev blkptr (the real error)
    2. spa_load_retry rewinds:  "spa_load_retry: rewind, max txg: 50"
    3. the rewind caps the acceptable uberblock below the label's own txg,
       so the best uberblock is now txg=42 while the label says txg=51
    4. the label is therefore discarded as "too large (51 > 42)"
    5. with no usable label the retry reports "label config unavailable"

Steps 2-5 are ordinary rewind machinery reacting to step 1. The debug hook is
not implicated. Recorded here because finding 16 flagged this as an open
"cause not determined" item and used it to justify calling the variant BLOCKED.

A TEMPTING HYPOTHESIS, CHECKED AND CLOSED
------------------------------------------
If the hole-vdev blkptr check in zfs_blkptr_verify() were NEWER than the
incident's build, its absence would neatly explain why the incident hung
where this synthesis fails fast. It is not newer. Checked by fetching each
release tag from github.com/openzfs/zfs on 2026-07-31 and grepping
module/zfs/zio.c for the "has hole VDEV" format string:

    zfs-2.2.2    present  (zio.c:1113)
    zfs-2.3.3    present  (zio.c:1290)   <-- the incident's lineage
    zfs-2.3.4    present  (zio.c:1290)
    zfs-2.4.1    present  (zio.c:1271)
    zfs-2.4.3    present  (zio.c:1271)
    master       present  (zio.c:1266)

The check is present in every release tested, including the one the incident
ran. This hypothesis is DISPROVED, and the incident's divergence remains
unexplained.


WHAT THIS ESTABLISHES
----------------------
STATED PLAINLY: **a hole vdev plus a dangling zh_log DVA resolving to it does
not hang a writable import on zfs-2.4.3 whether the chain is claimed or
unclaimed.** Unclaimed: imports cleanly, exit 0 (finding 16). Claimed: fails
fast with EIO at spa_load_verify, exit 1 (this file). Neither hangs, neither
produces a D-state task, and in the claimed case zil_check_log_chain() and
zil_parse() are both entered and both return.

The leading candidate for the incident's missing ingredient is therefore
closed, negatively.
